CSS ANIMATION PHILOSOPHY — SEED KNOWLEDGE
==========================================
Not a reference table of every preset. The underlying principles, so new
presets/combinations can be reasoned out, not just memorized. See
true_css_interpreter.txt for the original architecture this builds on.

THE CORE MODEL
---------------
A preset (css_presets/*.js) is a pure, reusable "brick": keyframes + easing,
nothing else. No timing, no target, no direction baked in. An animation_data
JSON file is the TIMELINE — it decides which bricks play, when, on whom,
and with what parameters. The engine (BattleScreen.jsx/VfxEditorScreen.jsx)
is a fixed, generic interpreter that never knows any specific attack exists.

The test for "is this actually data-driven": can a brand new attack be
built as a pure JSON diff, zero code changes? If yes, the system is working
as intended. Code changes are only for teaching the engine a genuinely NEW
CAPABILITY (a new channel, a new connector) — using that capability
afterward should always be pure data.

WHAT MAKES A PRESET A REAL "BRICK" (composable, order-independent) VS A
ONE-OFF WELDED TO ITS SPECIFIC NEIGHBOR: three connector conventions.
Skip these and a preset becomes secretly coupled to whatever's supposed
to run right before/after it — fragile, easy to desync later.

CONNECTOR 1 — DIRECTION (--dir)
--------------------------------
src/vfx/direction.js: getForwardSign(faction) -> 1 or -1.
Player's forward is up (negative Y), enemy's is down (positive Y), toward
each other. Computed FRESH from the real attacking character's faction
every time an animation plays (BattleScreen looks up gs.characters by
anim.ownerId/targetId) — never hardcoded per-attack.
Written into a preset as: calc(var(--dir) * Npx). One preset then serves
BOTH factions. The old anti-pattern this replaced: hand-mirrored duplicate
presets (speed_dash_lunge vs speed_dash_lunge_up) — same shape, opposite
sign, copy-pasted. Never do that again; use --dir instead.
Set on the element right before every playPreset() call, same spot as
the other two connectors below.

CONNECTOR 2 — MAGNITUDE (--distance / generic params)
--------------------------------------------------------
applyDynamicVars(el, params) in css_presets/index.js: any EXTRA key on a
css.target/css.owner JSON timeline entry gets forwarded 1:1 as a
same-named CSS var — { "distance": 26 } becomes --distance:26px, read via
calc(var(--distance)...) in the preset. A brand new parameter needs ZERO
code changes anywhere, as long as some preset's calc() reads the matching
var name. This is the general mechanism; --dir is really just the first
instance of the same pattern (computed instead of JSON-authored).
Mechanics/gotchas: see css_preset_guide_line.txt.

CONNECTOR 3 — POSITION CONTINUITY (--from-x / --from-y)
-----------------------------------------------------------
captureCurrentTransform(el) in css_presets/index.js reads el's ACTUAL
current rendered position and exposes it as --from-x/--from-y, called
right before EVERY playPreset(), same spot as --dir.
A preset written as translate(calc(var(--from-x) + 110px), var(--from-y))
instead of a hardcoded translate(110px, 0px) becomes truly reusable — it
continues correctly from wherever the PREVIOUS preset actually left the
element, in ANY order, with no manually-copied value that can drift out
of sync. This is what turns "chained presets" into genuine LEGO bricks
instead of presets secretly welded to one specific sibling.
Mechanics (why m41/m42, the translate-before-rotate ordering requirement,
the unverified 'none' edge case): see css_preset_guide_line.txt.

CHAINING / CONTINUITY RULE
----------------------------
Multiple timeline entries (css.owner: [{...},{...},{...}]) let one attack
compose several presets into a multi-phase motion via pure JSON sequencing
— no bespoke "combo" code per attack. Two ways to keep a chain visually
seamless (no pop between parts):
  a) Manually match values — preset B's first keyframe literally equals
     preset A's last keyframe value (works, but drifts if either changes
     later without updating the other — this caused a real bug once,
     dragon_step_right started at (0,0) instead of matching
     dragon_hard_step's actual ending transform).
  b) Use --from-x/--from-y (Connector 3) — no manual matching needed,
     can't drift, and presets built this way can chain in ANY order.
Prefer (b) for anything meant to be reusable across multiple attacks.

WHY SPLIT INTO MULTIPLE PRESETS AT ALL, INSTEAD OF ONE WITH MORE KEYFRAMES?
------------------------------------------------------------------------------
Only one real reason: playPreset() bakes ONE easing value onto every
keyframe in a preset (WAAPI's outer easing applies to the whole animation,
not per-segment like CSS @keyframes — see true_css_interpreter.txt gotcha
#2). If every phase of a motion shares the same easing, it should be ONE
preset with more keyframes — continuity is then already 100% free/native,
since keyframe-to-keyframe interpolation within a single animation needs
no --from-x/--from-y at all. Only split into separate chained presets when
different phases genuinely need different easing curves (e.g. a fast
ease-out snap forward vs a slow ease-in-out drift back — one shared curve
made the return spend most of its time still off-screen before rushing
into view at the very end, which is why ferret_pounce and straight_through
both got split this way).

FILL:'FORWARDS' — HANDLE WITH CARE
--------------------------------------
Default fill:'none' snaps back to the resting state the instant a preset's
animation ends, automatically, no cleanup needed. fill:'forwards' holds
the ending value indefinitely instead — but WAAPI composes MULTIPLE
overlapping animations on the same element/property by creation-order
stacking, not by "newest always wins forever." A fill:'forwards' preset
early in a chain can silently REASSERT its held effect later, after a
subsequent preset's own (temporary, fill:'none') effect naturally expires
— this is exactly what caused straight_through_exit to leave the card
stuck invisible off-screen after straight_through_return had already
finished and looked fine.
The fix in place: BattleScreen.jsx/VfxEditorScreen.jsx track every
Animation object a specific attack's own css.target/css.owner entries
spawn, then force-cancel ALL of them once the LAST entry's real end
(start+duration, computed from the entries themselves) is reached —
deliberately NOT tied to the JSON's top-level "duration" field, since that
also drives battle pacing (how long BattleScreen waits before the next
step) and can be intentionally SHORTER than the visuals it kicks off.
Cancelling removes an animation's effect entirely regardless of which
property it touched (transform, filter, opacity, boxShadow — anything),
so this cleanup is fully generic, not preset-specific.

CHANNEL LEGEND — ANIMATORS VS SPAWNERS
-------------------------------------------
The JSON channels divide by EXECUTION MODEL, not by visual theme:
  css  — ANIMATOR: animates the ONE existing element (WAAPI keyframes
         on the character card). Bricks live in css_presets/.
  dom  — SPAWNER: creates NEW DOM nodes, each with its own lifecycle
         (clones, echoes, decals). Bricks live in dom_presets/.
  pixi — SPAWNER: creates canvas particles (ThumosInterpreter).
  sfx  — sound.
The css/dom boundary is a hard capability line, not a style choice:
WAAPI's element.animate() can only change properties on an element that
already exists — it cannot create anything. Any effect that needs new
nodes (cloneNode/appendChild, staggered spawn timers, its own cleanup
path) is a dom preset, never a fake css preset. Candidates that belong
here as they get built: echo/delay clones, split-image feints,
persistent ground decals, DOM projectiles/shockwaves, shatter/debris.

THE DOM CHANNEL — CONTRACT AND FIRST PRESET (afterimage_trail)
------------------------------------------------------------------
config.dom mirrors config.css exactly — owner/target sides, entries of
{ "preset": <registry name>, "start": ms, "duration": ms, ...params }:
  "dom": { "owner": [
    { "preset": "afterimage_trail", "start": 0, "duration": 1200,
      "tickRate": 85, "count": 5 } ] }
TIMING IS ONLY A SWITCH. "start" turns the preset on, start+duration
turns it off — that is timing's ENTIRE footprint. The switch and the
effect's own params cooperate but never overlap: the switch says WHEN
the strobe runs, the params say what it does while running. (The old
channel's sin wasn't ticking — it was count x spacing forming a second
secret clock that kept spawning after the switch's window, i.e. after
the motion had stopped. The switch owns the window now; nothing else
has one.)
afterimage_trail is a STROBE — while on, every tick it leaves a frame
capture of the element exactly as rendered, no matter what the element
is doing:
  - it OBSERVES the rendered DOM (getBoundingClientRect +
    getComputedStyle transform each spawn) — never the css channel's
    config; the dom channel stays fully independent of how or why the
    element moves. Rotation/scale/skew replay on ghosts for free.
  - "tickRate" = ms between ghosts (clamped to TICK_RATE_MIN, 10).
    Authored in the same unit as the rest of the timeline — no
    cross-channel px math. Equal-TIME samples preserve the motion's
    speed texture, onion-skinning style: ghosts bunch where the card
    lingers, stretch apart where it snaps. (A distance-sampled version
    was tried and retired for flattening exactly that — see
    todo/afterimage_past.txt.)
  - "count" = hard cap on ghosts alive AT ONCE; spawning past it
    evicts the oldest into its own fade. Not a total.
  - each ghost is SELF-TERMINATING: spawns, fades over fadeDuration,
    removes its own node. Nothing manages a living ghost — the trail
    "ends" by its last ghost dying on its own, exactly like the
    original afterimage.js. The only ongoing thing needing external
    shutdown is the watcher loop (see containment below).
IMPLEMENTATION STATUS: dom_presets/afterimage_trail.js is live and
wired into both VfxEditorScreen and BattleScreen. The old top-level
config.afterimage channel is fully retired (history in
todo/afterimage_past.txt).
Each dom preset's implementation stays its own module for now; a shared
"DOM spawner engine" gets extracted only when a SECOND dom preset shows
which parts (observation, cleanup registry) are genuinely shared
rather than guessed.

DOM CHAINING + THE CONTAINMENT RULE
---------------------------------------
Multiple config.dom entries sequenced by "start" chain exactly like
css.owner entries do (afterimage burst during the dash, echo clone at
the strike, decal after) — the engine runs EVERY entry, and entries
from one attack must never interfere with another. A dom preset is a
FUNCTION (el, params) -> handle with TWO stop levels, WAAPI-style:
  finish() — soft stop: kills the preset's ongoing process (the
    watcher loop), while visuals already alive complete their own
    self-termination. The engine calls this on every handle at the
    chain's real end (computed from the entries' own start+duration,
    NOT the JSON's top-level pacing "duration" — that also drives
    battle pacing and can be intentionally shorter). Usually a no-op
    echo, since the preset's own duration deadline already stopped it.
  cancel() — hard stop: finish() plus immediate removal of every
    node still on screen. UNMOUNT ONLY (clearAllDomSpawns() in
    dom_presets/index.js — screens call it like clearAfterimageTimers)
    — the screen the ghosts float over is gone, so letting fades
    complete would strand nodes over an unrelated screen. Never call
    it at chain end: it visibly pops the still-fading tail of a trail
    out of existence.
Always play through playDomPreset(), never the preset module directly —
that's what enrolls a spawn's handle for unmount cleanup. Containment
stays airtight because self-termination is bounded: nothing a preset
spawns lives past its own fade. Effects that SHOULD persist past their
attack (lingering ground decals) will need an explicit opt-out param
on their entry when such a preset gets built; persistence must be
declared, never accidental.

AOE CAVEAT — OWNER-SIDE CHAINING IS NOT YET AOE-SAFE
----------------------------------------------------------
An AOE attack pushes ONE pendingAnimation entry PER TARGET HIT (see
reducer.js aoeHits.forEach), all sharing the same ownerId/attacker but
different targetId. Each entry independently re-triggers config.css.owner
— so a chained owner motion would fire once per enemy hit, nearly
simultaneously, competing with itself on the same attacker element.
config.css.target has no such problem (each hit is a genuinely different
element, correctly isolated). Rule of thumb: keep chained/continuity-
dependent motion (--from-x/--from-y presets especially) on css.target, or
scope css.owner chaining to single-target attacks only, until an AOE
guard (mirroring the existing skipSfx: i>0 pattern) gets built for the
owner side specifically.
